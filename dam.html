SMART Permission Tickets

A formal DAM artifact set for portable, scoped, auditable authorization across healthcare data access workflows. This artifact set converts the narrative DAM into reviewable models that can seed later IG, UML, sequence, requirements, and conformance work.

Source: 31 stakeholder interviews Basis: dam.md narrative DAM Status: working analysis artifact Generated: 2026-05-19

Domain Premise

The domain need is not merely a new token. It is a portable authorization mechanism that can be trusted, scoped, locally constrained, enforced, refreshed, revoked, and audited across multiple healthcare exchange contexts.

Narrative Anchor
Problem

Authorization is fragmented across portals, paper forms, local accounts, network agreements, app approvals, fax workflows, and local policy engines.

Boundary

A Permission Ticket sets an authorization ceiling. The data holder remains responsible for final release decisions and local filtering.

v1 Posture

Start with enforceable constraints: requester, recipient, subject, purpose, broad data category, time, case, claim, referral, condition, and organization.

Scope Model

The DAM scope separates the portable authorization mechanism from adjacent legal, consent, segmentation, and workflow integration workstreams.

Scope Artifact
In Scope
  • Portable authorization artifacts for healthcare data access
  • Patient, caregiver, payer, public health, registry, referral, backend, and network-mediated access
  • Issuer trust, requester identity, organization identity, client binding, subject resolution
  • Scope, duration, revocation, auditability, and discovery
  • Interaction with local policy, consent, DS4P-style segmentation, and jurisdictional rules at a conceptual level
Out of Scope
  • Final JWT schema or SMART grant specification
  • Universal patient identifier or single identity vendor
  • Complete consent form standard or clinical segmentation standard
  • Replacement for DUAs, BAAs, IRBs, laws, or network agreements
  • General write-back model for all EHR data
  • Full governance model for autonomous AI agents
Boundary principle: Permission Tickets should standardize the portable authorization context. They should not own every downstream clinical scoping taxonomy, consent form, segmentation rule, or data-use policy.

Actor and Responsibility Model

The actor model distinguishes who asserts permission, who requests data, who carries context, who enforces policy, and who is accountable for audit.

Actor Matrix
Actor Domain Responsibility Key Requirements Primary Risks
Authorizing Party Provides the basis for access: patient preference, caregiver authority, public health law, payer workflow, registry mandate, or provider action. Authority basis must be explicit and auditable. Ambiguous consent, expired authority, conflicting rules.
Issuer Mints and signs the Permission Ticket. Trusted for use context; keys discoverable; revocation supported; category membership governed. Misissued tickets, over-broad scope, conflict of interest.
Requester Presents the ticket to obtain data or a down-scoped access token. Must authenticate as intended client; must use ticket only within constraints. Replay, use by unintended client, downstream misuse.
Intermediary Carries, validates, transforms, or issues authorization context in network flows. Must preserve requester identity, purpose, role, organization, and scope. Target sees only intermediary; context is lost or altered.
Data Holder Validates ticket, applies local policy, resolves subject, issues or denies access. Can down-scope; local sensitive data filters remain authoritative. Over-release, wrong patient match, inconsistent API enforcement.
Subject The patient, member, or person whose data is requested. Subject resolution must be safe and auditable. Demographic mismatch, identity ambiguity, proxy conflict.

Ticket Lifecycle State Model

The state model separates the durable permission grant from short-lived access tokens and makes rejection, renewal, and revocation explicit.

Mermaid State Diagram

Permission Ticket Lifecycle

Conceptual state machine 
stateDiagram-v2
  [*] --> Draft: authority basis identified
  Draft --> Issued: issuer signs ticket
  Draft --> Abandoned: user or workflow stops
  Issued --> Presented: requester submits ticket
  Presented --> Rejected: invalid signature, issuer, audience, binding, subject, or revocation
  Presented --> Validated: ticket is structurally and cryptographically valid
  Validated --> DownScoped: local policy narrows authorization
  Validated --> Denied: local policy denies all access
  DownScoped --> TokenIssued: access token created
  TokenIssued --> Exercised: requester accesses API
  Exercised --> Refreshed: grant permits renewal
  Refreshed --> Presented: new token request
  Exercised --> Expired: ticket or token reaches time limit
  Issued --> Revoked: authorizing party or issuer revokes
  Presented --> Revoked: revocation discovered
  TokenIssued --> Revoked: active grant revoked
  Rejected --> Audited
  Denied --> Audited
  Exercised --> Audited
  Expired --> Audited
  Revoked --> Audited
  Audited --> [*]

Risk and Mitigation Matrix

The DAM risk model captures the failure modes most likely to undermine adoption, safety, or trust.

Risk Artifact
Risk Impact Mitigation Residual Open Question
Over-provisioning Unauthorized or excessive disclosure. Ticket is ceiling; data holder down-scopes; conformance tests verify enforcement. How much policy language belongs in the ticket versus local configuration?
Under-provisioning Legitimate care, public health, or registry work is blocked. Support renewal, follow-up tickets, partial denial reasons, and use-case profiles. Who defines condition-specific and workflow-specific scope profiles?
Wrong-patient match High-severity privacy and safety failure. Prefer solid identifiers; separate demographic matching; deny ambiguity. What minimum identifier assurance is acceptable for each use case?
Issuer misuse Trust framework collapse or broad unauthorized access. Use-case-specific issuer accreditation, audit, suspension, and revocation. Which entity governs issuer accreditation?
Category surprise Practices lose control over approved requester categories. Notify, lock membership, or require reapproval for material changes. What counts as a material category change?
Sensitive data leakage Behavioral health, 42 CFR Part 2, sexual health, or self-pay data disclosed improperly. Keep local filters authoritative; align with DS4P; avoid unsupported fine-grain claims. What segmentation level can EHRs reliably support in v1?
Post-release misuse Ticket controls access but not downstream behavior. Preserve purpose, recipient, audit, provenance, and legal agreements. Should later work explore object-capability or data-use controls?
Implementation burden Spec validates but does not get adopted or enforced consistently. Reference implementation, test suite, phased profiles, and open deployment path. What minimum viable deployment package is needed?
